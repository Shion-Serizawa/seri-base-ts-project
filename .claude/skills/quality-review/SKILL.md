# 品質レビューを観点ごとに分けて回す

このリポジトリの Maker–Checker は「決定論的ゲート（適応度関数 ①〜⑱）」と
「別コンテキストのレビュー」の 2 段で成り立っている（[CLAUDE.md](../../../CLAUDE.md) の
「検証（Maker–Checker）」節）。この手順は後者のためのもので、**前者が見ているものは
対象外**である。観点と発火条件の背景は
[docs/quality/iso25010.md](../../../docs/quality/iso25010.md)、
判断の経緯は [docs/adr/0009-iso25010-review-layer.md](../../../docs/adr/0009-iso25010-review-layer.md)
にある。**ここでは再掲しない。**

## 0. 前提: ゲートを先に通す

レビューはゲートの代わりではない。先に決定論側を通しておく。

```bash
bun run lint
bun run typecheck
bun run test
bun run fitness
```

**ここが赤いままレビューを始めない。** ゲートが落ちている状態の指摘は、
ゲートの指摘とレビューの指摘が混ざって、どちらも読まれなくなる。

## 1. 起動する観点を決める（人でも AI でもなく、スクリプトが決める）

```bash
bun run review:plan
```

[scripts/review/route.ts](../../../scripts/review/route.ts) が変更されたパスから
観点を決め、観点ごとのプロンプト断片を出力する。

**この判定を自分でやり直さない。** 「この変更なら性能は関係ないだろう」と観点を
間引くと、レビューは「実施済み・指摘なし」を返す。それは
[ADR 0002](../../../docs/adr/0002-fitness-functions.md) が記録している
「ゲートが黙って緑だった」と同じ壊れ方で、しかも検出手段が無い。
発火条件がおかしいと思ったら、その場で間引くのではなく `route.ts` を直して
テストを足す（誤検出も検出漏れもテストで固定してある）。

出力の末尾に「今回は起動しない観点」が出ることがある。同時起動の上限
（常設 2 + 条件付き 3）で溢れた分で、**該当はしている**。上を片付けてから
必要に応じて個別に起動する。

## 2. 観点ごとに独立したサブエージェントを起動する

**1 つのコンテキストで複数の観点を見ない。** 観点を混ぜると、先に見つかった
指摘に引きずられて残りが浅くなる。`bun run review:plan` が出したブロックは
1 つで完結しているので、ブロックをそのまま 1 エージェントに渡す。

各エージェントに渡すもの:

1. `review:plan` が出したその観点のブロック（そのまま貼る）
2. 対象の差分（`git diff <基準>...HEAD` の範囲。基準は `review:plan` と揃える）
3. 次の指示（そのまま渡す）

```
あなたはこの観点だけを見る。他の観点の指摘はしない。

- ブロックの「既存ゲートが見ている」に挙がっているものは指摘しない。
  それらは決定論的ゲートが落とすので、ここで見るのは二重になる。
- 「証拠として出すもの」を必ず埋める。埋められない指摘は
  「疑い」として別の節に分けて出す。
- 実際にファイルを読み、テストを実行して確かめる。
  終了コードと出力を見ずに「通っている」と書かない。
- 指摘には必ずファイルと行を付ける。
- 指摘が無いなら「無い」と書く。無理に挙げない。
```

サブエージェントは**読み取りと検証だけ**を行う。修正はしない。
複数の観点が同じ箇所を別々に直すと、どの指摘に対する修正なのか追えなくなる。

## 3. 組み込みの `/code-review` を併用する

組み込みの `/code-review` には観点を渡せない（引数は対象と effort、
`--comment` / `--fix` だけ）。見るのは correctness bug と
reuse / simplification / efficiency に固定されている。

そこで**置き換えずに併用する**。バグ検出の 1 本として走らせ、
この手順は「ゲートも `/code-review` も見ない観点」を担当する。
重複した指摘が出たら、この手順側を捨てる（相手は環境側の資産なので）。

## 4. 結果をまとめる

観点ごとの報告を 1 つにまとめ、次の形で出す。

- **証拠のある指摘**（観点 / ファイル:行 / 何が壊れるか / 証拠）
- **疑い**（証拠を出せなかったもの。放置してよいが、消さない）
- **今回起動しなかった観点**（上限で溢れたもの）

作業ディレクトリが必要なら `.review/`（`.gitignore` 済み）を使う。

## 5. 直すときの決まり

- **ゲートを緩める・テストを消す・`// @ts-expect-error` を足すで通さない**
- 同じ失敗を 3 回繰り返したら止めて相談する
- しきい値の変更、ゲートの追加・削除、層の依存の変更、
  **レビューで見つかった穴**は ADR に残す（[CLAUDE.md](../../../CLAUDE.md) の規約）
- 発火条件の穴が見つかったら `route.ts` にテストを足して塞ぐ。
  「実リポジトリで PASS すること」は誤検出が無い証明にならない
  （[ADR 0002](../../../docs/adr/0002-fitness-functions.md) の教訓）

## この手順を外したときに何が起きるか

- 観点を混ぜて 1 回で見る → 見落とす。誰も検出できない
- `review:plan` を使わず自分で観点を選ぶ → 落とした観点が「指摘なし」になる。誰も検出できない
- 証拠なしの報告を受け入れる → 「大丈夫です」だけが残る。誰も検出できない

決定論的に守れるのは `route.ts` の発火条件だけで、**2 と 4 は自分で守るしかない**。
