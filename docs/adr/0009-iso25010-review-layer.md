# 0009. ISO/IEC 25010 を「空白領域を埋める分類」として使い、レビューを観点ごとに分離する

- 日付: 2026-09-06
- 状態: 採用

## 背景

[0007](0007-ai-coding-context.md) で Context 層と Maker–Checker の方針を決めたが、
レビュー側は「別コンテキストで `/code-review` を回す」という一文しか無かった。
実際に回すと、1 つのコンテキストで仕様・設計・セキュリティ・信頼性を同時に見ることになり、
先に見つかった指摘に引きずられて残りが浅くなる。

そこで ISO/IEC 25010:2023 の 9 特性をレビューの軸として使うことを検討した。
検討の出発点にした整理は「常設コンテキスト → トリガー → 自動検査 → AI による意味論的レビュー」
という 4 段構えで、`.ai/` 配下に 9 特性 × 観点文書 + レビュー手順 + トリガー定義を置き、
PR ごとに AI を「品質分類器」として走らせる、というものだった。

そのままは採用しなかった。理由は 3 つある。

### 1. 9 特性のうち 6 つは既に埋まっている

現状を 9 特性で棚卸しすると、空白は 3 つだけだった。

| 特性         | 現状の強制手段                                                  | 評価                                   |
| ------------ | --------------------------------------------------------------- | -------------------------------------- |
| 機能適合性   | ① カバレッジ / ④ ミューテーション / `*.test-d.ts`               | 手段は強い。照合先の「仕様」だけが無い |
| 保守性       | ③⑤⑥⑥′⑦⑪ + `any` 禁止                                            | 13 ゲート中の過半。突出して強い        |
| セキュリティ | ⑨ / `bun audit` / Actions 固定 / `os` の型強制 / CORS allowlist | 最も作り込まれている。SAST だけ無い    |
| 互換性       | ⑫ 契約と OpenAPI の乖離 / ⑩ スキーマ乖離                        | **破壊的かどうかは人が差分を見る運用** |
| 相互作用能力 | oxlint の `jsx-a11y`                                            | 静的な JSX の不備のみ                  |
| 柔軟性       | `process.env` 禁止 / `domain` の決定性禁止則                    | 設定のハードコードは未検査             |
| 性能効率性   | ⑧ バンドルサイズ予算                                            | ほぼ空白                               |
| 信頼性       | **なし**                                                        | 空白                                   |
| 安全性       | **なし**                                                        | 空白                                   |

9 特性を等しく扱う設計にすると、既に埋まっている 6 つに文書とレビューのコストを払うことになる。
**25010 は「網羅すべきチェックリスト」ではなく「空白を見つける分類」として使う。**

### 2. `.ai/` に 18 ファイル置く構成は規模と思想の両方に合わない

実装ファイルは `apps` + `packages` で約 25 本しかない。そこに観点文書 9 本 +
レビュー手順 5 本 + トリガー定義 4 本を置くと文書が実装に匹敵する。
[0007](0007-ai-coding-context.md) は既に「10〜30 名・3〜5 リポジトリ前提の資料を
そのままの規模で入れない」と決めており、[CLAUDE.md](../../CLAUDE.md) は
「詳細を再掲しない・索引に徹する」を明文化している。

加えて ⑬ の性質上、**AI に読ませる文書を増やすほど参照切れの面積が増える**。
[0002](0002-fitness-functions.md) は「文書を厚くしすぎると ⑬ が壊れやすくなる」と
自ら記録している。

### 3. 「AI を品質分類器にする」は、このリポジトリが繰り返し踏んだ地雷

元の整理の中核は、PR ごとに LLM に diff を読ませて「実質的に影響を受ける品質特性」を
選ばせる Quality Router である。しかし分類器が観点を 1 つ黙って落としたとき、
レビュー層は「実施済み・指摘なし」を返す。これは
[0002](0002-fitness-functions.md) の「ゲートが 2 件黙って緑だった」、
[0005](0005-authorization-and-cors.md) の「8 つのゲートが全く鳴らなかった」と
完全に同型の事故で、しかも**検出手段が無い**。

## 決定

### 1. 決定論に降ろせるものはゲートにする（⑯ ⑰）

空白 3 領域のうち、**今すぐ証拠が取れるもの**だけをゲート化した。

- **⑯ OpenAPI の破壊的変更**（互換性）— ⑫ は乖離しか見ないので、契約と一緒に
  ドキュメントを再生成すればフィールドを消しても緑で通っていた
- **⑰ 破壊的マイグレーション**（安全性）— ⑩ は乖離しか見ないので、列を消す
  マイグレーションを正しく生成すれば緑で通っていた。D1 に巻き戻しは無い

いずれも「通す唯一の手段が意図の宣言」になっており、回避しても記録が残る
（⑯ は Conventional Commits の `!` / `BREAKING CHANGE:`、⑰ は SQL ファイル内の
`-- destructive: <理由>`）。指標の詳細は [0002](0002-fitness-functions.md) を参照。

### 2. 観点文書は 1 ファイルだけにする

[docs/quality/iso25010.md](../quality/iso25010.md) 1 本。9 ファイルに割らない。
実体は [scripts/review/dimensions.ts](../../scripts/review/dimensions.ts) にあり、
**文書とコードがずれていないことを
[scripts/review/route.test.ts](../../scripts/review/route.test.ts) が検証する**
（⑬ はパスの実在しか見ないので、中身の一致は別に固定する必要がある）。

[CLAUDE.md](../../CLAUDE.md) への追記は索引 1 行に留めた。

### 3. ルーティングは決定論、判断だけを LLM に

これがこの ADR で最も重要な分岐点である。

```
git diff --name-only
        ↓
scripts/review/route.ts   ← 純関数・テスト付き
        ↓
bun run review:plan       ← 起動すべき観点 + プロンプト断片
        ↓
観点ごとに独立したサブエージェント（常設 2 + 条件付き 3 まで）
        ↓
.review/ に「主張 + 証拠」で出力
```

- 発火条件は「変更パス → 品質特性」の純関数。誤検出と検出漏れの**両方**をテストで固定した
  （[0002](0002-fitness-functions.md) の「実リポジトリで PASS することは誤検出が無い証明にならない」）
- 上限で溢れた観点は捨てずに `deferred` として出力に残す。**黙って消すと、
  見ていないのに見たことになる**
- 各サブエージェントには「既存ゲートが見ているもの」を渡し、二重の指摘を禁じる
  （[CLAUDE.md](../../CLAUDE.md) の「決定論的に検出できるものはゲートに任せ、二重にやらない」）
- 報告は「主張ではなく証拠」。観点ごとに要求する証拠を `dimensions.ts` に持たせた

手順は [.claude/skills/quality-review/SKILL.md](../../.claude/skills/quality-review/SKILL.md)。

### 4. 組み込みの `/code-review` は置き換えず併用する

調査の結果、**組み込みの `/code-review` に観点は渡せない**。引数は対象（diff / PR / ブランチ /
パス）と effort level と `--comment` / `--fix` だけで、見る軸は correctness bug と
reuse / simplification / efficiency に固定されている。実体は CLI 内蔵でディスク上に無く、
差し替えもバージョン管理もできない。プラグイン版の `code-review` は PR 前提（`gh` 必須）で、
5 エージェントの観点がコマンド定義にハードコードされている。

したがってバグ検出の 1 本として併用し、この層は「ゲートも `/code-review` も見ない観点」を
担当する。副次的に、[0007](0007-ai-coding-context.md) が「残る穴」に挙げた
**`/code-review` が環境側依存でリポジトリに実体が無い**問題が部分的に解消した
（観点と発火条件はリポジトリ内にあるので、環境が変わっても黙って失われない）。

### 5. 保守性には名前の付いた症状を持たせ、機能適合性には照合先を要求する（2026-09-06 追記）

運用の参考にした二軸レビュー（Standards / Spec）の手順を読み直したところ、
**軸そのものは既に入っていた**。常設の 2 観点がそれで、機能適合性が Spec 軸、
保守性が Standards 軸にあたる。足りていなかったのは 3 点で、いずれも埋めた。

**(a) 保守性の語彙が粗すぎた。** 「責務・命名・重複・変更局所性」の 4 つだけだと、
レビューする側の語彙に依存して見落ちる。Fowler『リファクタリング』第 3 章の
12 の症状を [scripts/review/smells.ts](../../scripts/review/smells.ts) に置き、
保守性の観点にだけ添えるようにした。2 つの拘束をかけている。

1. **リポジトリの規約が優先する。** 規約は機械化してあるので、症状と衝突したら規約が正しい
2. **すべて判断であって違反ではない。** 確実に落とせるものは ③⑤⑥⑦ が既に落としている。
   症状の指摘は原則「疑い」の側に置く

**(b) 機能適合性が「何と照合するか」を言っていなかった。** 照合先を渡さずに起動すると、
エージェントは実装を読んで「実装のとおりに動いている」と書く。それは何も検証していない。
照合先を「依頼 → ADR → 契約 → 既存テスト」の順で探し、**見つからなければ
『仕様が無い』と報告する**ことを要求した。無いことを「指摘なし」にしない。

**(c) 基準リビジョンを確かめる手順が無かった。** 解決しない基準や空の差分で始めると、
全観点が「指摘なし」を返す。「見た結果、問題が無かった」と区別が付かない。
サブエージェントを起動する前に `git rev-parse` と `git diff --stat` で確かめ、
駄目なら止めることにした。⑧ の未ビルドや ⑯ の基準未解決と同じ「計測不能」である。

**二軸を統合しないことも明記した。** 規約どおりだが作っているものが違う変更と、
依頼どおりだが流儀を壊している変更は独立に起きる。観点をまたいで順位を付け直すと、
片方がもう片方を隠す。観点を分けた理由そのものが失われる。

症状の一覧が文書とコードでずれないことは
[route.test.ts](../../scripts/review/route.test.ts) が検証する（観点のキーと名前に
対して既にやっているのと同じ扱い）。

## 入れなかったもの

| 見送ったもの                           | 理由                                                                                     |
| -------------------------------------- | ---------------------------------------------------------------------------------------- |
| `.ai/` の 18 ファイル構成              | 背景 2。索引主義と ⑬ に反する                                                            |
| 9 特性 = 9 エージェント                | 個人開発で重すぎ、回さなくなる。上限を常設 2 + 条件付き 3 にした                         |
| LLM による品質分類（Quality Router）   | 背景 3。レビュー層の false green                                                         |
| QPS / SLO / データ量の常設コンテキスト | **数字が存在しない。書けば嘘になる**                                                     |
| k6 / EXPLAIN 回帰 / Fault Injection    | 本番も負荷も利用者も無い。証拠が作れないものをゲートにすると「計測不能」が緑で出る       |
| Semgrep / CodeQL                       | 認可は型で落ちる設計（⑭）。費用対効果が薄い                                              |
| N+1 検出のゲート化                     | ループ内 await の静的検出は誤検出が多い。「うるさいから外される」パターンに嵌まる        |
| 外部 I/O の timeout ゲート             | 現状 `fetch` がほぼ無く効果ゼロ。実際に外部 I/O を足す時点で入れる                       |
| Nightly CI                             | 個人開発・無料枠。PR と pre-push で足りる                                                |
| レビュー実施の hook 強制               | [0007](0007-ai-coding-context.md) が hook を増やすなと決めている。実施記録の最適化を招く |

## 結果

- 適応度関数が 13 件から 18 件になった（⑭ ⑮ ⑱ は別途追加。`bun run fitness` の件数は 16）
- `scripts/review/`（`dimensions.ts` / `route.ts` / `plan.ts` / `run-plan.ts`）と
  `bun run review:plan` を追加した
- `.claude/skills/quality-review/SKILL.md`、[docs/quality/iso25010.md](../quality/iso25010.md) を追加した
- `FitnessContext` に `baseRef` を足した（⑯ が基準リビジョンとの差分を取るため）。
  既定は `main`。リモートを設定していないローカルでも解決できるようにするため
  `origin/main` にはしていない

### 実装中に既存ゲートが 2 件検出した

- ⑥′（`knip --production`）が `MAX_CONDITIONAL` を「テストのためだけの export」として
  検出した。[0002](0002-fitness-functions.md) が記録している同じパターンの 3 例目
- ⑬ が `quality-review` スキルからの ADR 0009 への参照切れを検出した（この文書が
  書かれる前の状態）

### ⑯ の基準リビジョンで false green を 1 つ塞いだ

当初 `origin/main` を既定にしていたが、このリポジトリにはリモートが無く常に FAIL した。
`main` に変えたところ、今度は **main の上で作業しているときに基準と HEAD が同じコミットになり、
差分が空になって「破壊的変更なし」を返す**ことが分かった。
基準が HEAD と一致する場合だけ `HEAD~1` に落とし、**落としたことを結果に出す**ようにした
（比較の幅が狭いこと自体が情報なので黙って落とさない）。
④ ミューテーションが PR のみで牽制が外れていたのと同じ形の穴である。

## 残る穴

- **信頼性はゲートが 1 つも無い**。タイムアウト・再試行・冪等性・トランザクション境界は
  レビュー観点にしか無く、レビューを回さなければ何も見ていないのと同じ
- 発火条件はパスだけを見ている。「`catch` を足した」「`fetch` を足した」といった
  diff の内容によるトリガーは実装していない。パスで十分でない事例が出てから足す
- サブエージェントの報告の質は機械的に検証できない。「証拠を出せ」と指示しても、
  証拠を捏造されたら検出できない。決定論的に守れるのは発火条件だけである
- `apps/web/src/routes/**` が未検証（E2E 未着手）という [0002](0002-fitness-functions.md) からの
  既存の穴は、この層では埋まっていない
