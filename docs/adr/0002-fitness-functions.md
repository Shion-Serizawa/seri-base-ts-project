# 0002. 適応度関数（グッドハート対策）

- 日付: 2026-08-23
- 状態: 採用

## 背景

AI Coding では指標が「達成すべき目標」として直接最適化される。単一指標を置くと、
コードの質ではなく**指標の数値だけ**が最適化される（グッドハートの法則）。

代表的なハック:

- カバレッジ 80% → アサーションのないテストを大量に書く
- test ratio 下限 → テストをコピペで膨らませる
- 循環的複雑度の上限 → 意味のない小関数に分割して薄く散らす
- 複雑度・カバレッジの達成 → 巨大なライブラリを持ち込んで自前ロジックを消す

## 決定

**単独でハックすると別の指標が悪化する**組み合わせを適応度関数として設定する。
しきい値は `tooling/quality-gates/src/index.ts` に集約し、外部ツールの設定ファイル
（`.oxlintrc.json` / `stryker.config.json` / `.jscpd.json`）の数値と一致していることを
`tooling/quality-gates` のテストが検証する。**設定ファイル側だけを緩める**という
最も安易な抜け道を塞ぐのが目的。

### 牽制の構造

```
① カバレッジ 80%（ファイル単位）
   └ ハック: アサーションなしテスト
       ├ ④ ミューテーションスコア 60%（アサーションがないとミュータントが生き残る）
       └ vitest/expect-expect（そもそも lint で落ちる）

② test ratio 上限 2.50（下限は置かない。理由は後述）
   └ ハック: テストのコピペ膨張
       ├ ② の上限そのもの
       └ ③ 重複率 3%（jscpd はテストコードも対象にしている）

③ 重複率 3%
   └ ハック: 過度な共通化・抽象化
       └ ⑤ 複雑度（共通化した関数が太る）

⑤ 循環的複雑度 10 / ネスト 3 / 関数 50 行 / 引数 4 / 文 20
   └ ハック: 無意味な関数分割で薄く散らす
       ├ ⑥ knip（使われない export が出れば落ちる）
       └ ③ 重複率（分割した断片が似通れば落ちる）

⑧ バンドルサイズ予算（gzip）
   └ ①⑤ を「依存を足して楽をする」方向で満たそうとすると落ちる

⑨ シークレットの混入（gitleaks / 作業ツリー + git 履歴）
⑩ スキーマとマイグレーションの乖離（drizzle-kit）
   └ ⑨⑩ は牽制関係ではなく、型でもテストでも守れない性質のものを直接見ている
```

### 強制する場所

「速いものは pre-commit、型情報が必要なものは pre-push、重いものは CI」で分けている。

| 指標                                     | 場所                                 | 理由                           |
| ---------------------------------------- | ------------------------------------ | ------------------------------ |
| 複雑度・`any` 禁止・層の境界             | pre-commit（差分）/ pre-push（全体） | oxlint は差分なら 1 秒未満     |
| カバレッジ                               | pre-push / CI                        | テスト実行が必要               |
| test ratio・重複率・デッドコード・サイズ | pre-push / CI（`bun run fitness`）   | 数秒                           |
| ミューテーションスコア                   | CI（PR、変更ファイルのみ）           | 全体実行では時間がかかりすぎる |

### `any` は割合ではなく error で禁止する

type-coverage による「型カバレッジ 99%」のような割合指標は、
残り 1% をどこに使うかの判断が属人化し、AI にとっては「1% までは `any` を書いてよい」
という指示になってしまう。次のルールで **error** として禁じる。

- `typescript/no-explicit-any`
- `typescript/no-unsafe-assignment` / `-argument` / `-call` / `-member-access` / `-return`
- `typescript/no-unsafe-type-assertion`（`as` による不正な絞り込みも禁止）
- `typescript/ban-ts-comment`（`@ts-expect-error` は 10 文字以上の理由必須、`@ts-ignore` は禁止）

## 却下した案

- **カバレッジ 100%**: 到達コストが指数的に上がり、意味のないテストを誘発する。80% + ミューテーションスコアの方が実質的
- **test ratio の下限**: 当初 0.50 を下限として設定したが撤去した。理由は下記
- **warn から始めて段階的に error へ**: AI は warn を無視して進むため牽制力が落ちる。空のリポジトリなので最初から error にしても既存コードの負債はゼロ
- **差分のみに閾値を適用（diff coverage 方式）**: 設定が複雑になる。レガシーを抱えた時点で再検討する
- **認知的複雑度（SonarJS）の別途導入**: oxlint の `complexity` + `max-depth` + `max-lines-per-function` + `max-params` の組み合わせでほぼ代替でき、ESLint 併用の保守コストを払う価値がない

## test ratio の下限を撤去した理由（2026-08-24）

当初は「テストが薄すぎる状態」を検出するために下限 0.50 を置いていたが、次の理由で撤去した。

1. **良い書き方を罰する。** `it.each` によるテーブル駆動化は、テスト行数を減らしながら
   カバレッジとミューテーションスコアを上げる。下限があるとこれが減点になる
2. **量を足す方向の圧力になる。** 実際にこのリポジトリで、実装が増えてテストを整理した結果
   0.4986 になり、下限を満たすためにテストを追加した。今回は本当に抜けていた箇所
   （状態遷移の通し確認）だったので結果的に良かったが、判断が別方向に転べば水増しだった
3. **代替がある。** 「テストが足りない」の検出は、カバレッジを**ファイル単位**
   （`coverage.thresholds.perFile`）にする方が正確。集計だと、十分テストされた他のコードに
   紛れて「テストが 1 件も無いファイル」が隠れる

実際、perFile を有効にした直後に 2 件の実質的な穴が出た。片方は
`createQueryClient` のテストを消してしまった回帰、もう片方は
`api-client.ts` がテストで常にモックされていて一度も実行されていなかったこと
（`credentials: 'include'` を付ける fetch ラッパが未検証だった）。
LOC 比では検出できなかった種類の穴である。

**上限は残した。** 20 行の実装に 500 行のテストを書く方向（特に AI に「テストを増やせ」と
指示したとき）は、他のどの指標も測っていない。

## 型そのものの検査（2026-08-24 追加）

このリポジトリでは型が主要な成果物（branded type、oRPC の契約）なので、
`vitest --typecheck` による型テスト（`*.test-d.ts`）を `packages/contract` に置いている。
「型が緩くなる」方向の退化は実行時テストでは検出できない。

この型テストは導入直後に設計上の誤解を検出した。zod の `.brand()` が型を付けるのは
**出力側だけ**で、入力（`z.input`）は生の string のままである。つまり API 呼び出しの引数には
string を渡せる。branded type が守っているのは「受け取った id を他の string と混同すること」
であって、呼び出し時の入力ではない。この非対称性は型テストに固定してある。

## レビューで判明した穴と対応（2026-08-25）

第三者によるレビューで、実際に設定を改ざんして検証した結果いくつかの穴が判明した。

### 1. 「設定だけ緩める抜け道を塞ぐ」が複雑度の 7 つの数値にしか効いていなかった

最も強く主張していた防御が、実際には `complexity` / `max-depth` / `max-params` /
`max-statements` / `max-nested-callbacks` / `max-lines-per-function` / `max-lines` の
**数値 7 つしか見ていなかった**。以下の改ざんはテストを 1 つも落とさなかった。

```
"correctness": "error"       → "off"   （バグ検出カテゴリ丸ごと）
"typescript/no-explicit-any" → "off"
"vitest/expect-expect"       → "off"   （カバレッジ水増しの唯一の門番）
```

ゲートに詰まったときの最短の修復手段がそのまま通る状態だった。

対応: `tooling/quality-gates/src/lint-policy.ts` に Lint 設定のポリシーを宣言し、
`lint-policy.test.ts` が `.oxlintrc.json` との一致を検証する。

- `categories` は完全一致
- `error` にしているルールの集合が完全一致（消しても off にしても落ちる）
- `off` にしているルールの集合が完全一致（新しい off を勝手に増やせない）
- `warn` の使用を禁止（AI は warn を無視して進むため）
- `overrides` で off にできるルールを allowlist で制限（`typescript/no-unsafe-*` を
  ディレクトリ単位で黙らせる抜け道を塞ぐ）

上の 3 つの改ざんを再現し、3 件のテストが落ちることを確認した。

### 2. 層の境界がサブパス import で素通りしていた

`no-restricted-imports` を `paths`（完全一致）で書いていたため、`@seri/db` は止まっても
`@seri/db/schema` は通っていた（`@seri/db` は実際に `./schema` を exports している）。
また `apps/web` の制限リストには `@seri/api` しかなく、web → db は無防備だった。

対応: `patterns`（glob + `!` による許可）に変更し、各層を
「許可する依存先の allowlist」として書き直した。`@seri/db/schema` と
web からの `@seri/db` の両方がブロックされることを確認した。

### 3. デッドコード指標がテスト 1 本で無力化できた

`knip.json` の `entry` にテストファイルを入れていたため、テストから参照された export は
「使用中」扱いになっていた。**⑥ を無力化する行為が同時に ① カバレッジと
② test ratio を改善する**という、牽制構造が逆向きに働く唯一の箇所だった。

対応: 本番の入口を `!` サフィックスで明示し、`knip --production` を別ゲートとして追加した。
導入直後に「テストからしか使われていない export」を 5 件検出した
（`apps/api/src/index.ts` 全体、`RPC_PREFIX`、`apiOrigin`、`authClient`、
`todoContract`、`TODO_TITLE_MAX_LENGTH`）。いずれも削除または非公開にした。

### 4. バンドルサイズが未ビルドだと緑になっていた（false green）

`dist` が無いとき `ok: true` を返していた。pre-push は build を回さないため、
クローン直後や dist 削除後は常に PASS 表示だった。「計測できなかった」が緑で出るのは
最も危険な表示なので、**計測不能を失敗として扱う**ようにし、
pre-push に build を追加した（turbo のキャッシュが効くので差分が無ければ数百ミリ秒）。

### 5. test ratio が全体の 1 つの数値だった

どこが厚い／薄いのかが分からず、AI にフィードバックできなかった。
ワークスペース単位で算出・表示し、判定も各ワークスペースに対して行うようにした。

### 6. ミューテーションが PR のみだった

`if: github.event_name == 'pull_request'` だったため、main への直 push では ④ が走らず
① の牽制が外れていた。push でも走るようにし、差分の基準を
PR ならベースブランチ、push なら `HEAD~1` に切り替えるようにした。

### 対応しなかったもの

- **`apps/web/src/routes/**` が無防備**（テスト無し・カバレッジ除外・E2E 無し）。
  E2E を入れる段階でまとめて対応する

## 適応度関数そのものをテストした（2026-09-05）

上記 4 と 5 の不具合はどちらも未テストのスクリプトコードのバグだった。
「ゲートを実装したコードにバグがあると、ゲートが黙って緑になる」という壊れ方は
型検査でも他のテストでも捕まらないので、`scripts/` を計測とテストの対象に入れた。

### 何を変えたか

検査が `process.cwd()` と実際のプロセス起動に直接依存していたため、
そのままではテストできなかった。`FitnessContext`（`root` / `run` / `ci`）を
引数として渡す形に変え、テストは一時ディレクトリに作った擬似リポジトリと
差し替えた `run` に対して検査を走らせる。knip も gitleaks も起動せずに、
**終了コードの解釈・出力の整形・PASS/FAIL の判定**を検証できる。

`process.exit` を呼ぶだけの実行入口（`run.ts` 等）は判定ロジックを持たない数行に切り詰め、
カバレッジ計測から外している。判定は全て別モジュールにある。

ルートワークスペースのタスクは turbo の `//#` 記法で回す
（`turbo run test:coverage '//#test:scripts:coverage'`）。

### ⑥′ が設計を直した

内部ヘルパを「テストから呼ぶため」に export したところ、
`knip --production` が 13 件の未使用 export として検出した。
これは ⑥′ が想定どおりに働いた例で、**テストのためだけの export** を許すと
「テストを 1 本足して使用中にする」抜け道と同じことになる。
export を戻し、テストは公開している検査関数（`checkSizeBudget` など）を通す形に直した。

その過程で、予算超過の挙動を現実的な大きさのフィクスチャで検証できるよう
`checkSizeBudget(context, budget)` の第 2 引数を足している
（既定値は `QUALITY_GATES` のままなので単一情報源は変わらない）。

## ⑫ 契約と OpenAPI ドキュメントの乖離（2026-09-05 追加）

`packages/contract` から `docs/openapi.json` を生成し、コミット済みの内容と一致することを
検証する。⑩ スキーマとマイグレーションと同じ「型検査もテストも通るのに
公開している情報だけが古い」型の壊れ方を防ぐ。詳細は
[0006-openapi-generation.md](0006-openapi-generation.md)。

## ⑬ Context の陳腐化（2026-09-05 追加）

`CLAUDE.md` と `.claude/skills/**/SKILL.md` が参照しているファイルパスと `bun run` の
スクリプトが実在することを検証する。文書が古くなる壊れ方は誰にも見えない。AI は
存在しないパスを黙って諦め、存在しないコマンドを打って別の理由で失敗するので、
原因が文書の陳腐化だと気づけない。lint も型検査もテストも markdown を見ない。

**牽制関係**: ⑬ を通す一番安易な方法は「文書を消す」なので、文書が 1 つも無い場合を
FAIL にしている（⑧ の未ビルドと同じ扱い）。逆に文書を厚くしすぎると参照が増えて
⑬ が壊れやすくなるので、`CLAUDE.md` を索引に徹させる圧力にもなっている。

バッククォートで囲まれたパスを拾う対象は、先頭がワークスペースのディレクトリ名
（`apps` / `packages` / `tooling` / `scripts` / `docs`）のものに限っている。
`/api/rpc` のような URL や `<resource>.ts` のようなプレースホルダを誤検出しないため。

導入の経緯と、Graph やエージェント基盤を入れなかった理由は
[0007-ai-coding-context.md](0007-ai-coding-context.md)。

### ⑬ が実装中に自分自身のバグを 2 件見つけた

- 内部ヘルパ `listContextDocuments` を不要に export していた（⑥ knip が検出）。
  ⑥′ が設計を直した件と同じパターン
- ワークスペースの scripts を `package.json` の**文字列一致**で探していたため、
  `@seri/db` に依存しているだけの `apps/api` を先に拾い、
  `bun run --filter @seri/db db:generate` を「存在しない」と誤答していた。
  `name` と厳密に突き合わせる形に直し、この誤認のテストを足した

2 件目は「FAIL するはずのないものを FAIL にする」側の誤りで、false green とは逆向きだが、
放置すれば「うるさいから」とゲートごと外される。実リポジトリに対して一度走らせるまで
気づかなかったので、新しい検査は擬似リポジトリのテストに加えて `bun run fitness` を
必ず通すこと。

## 運用

`bun run fitness` が 13 件をまとめて計測し、表で結果を出す。
しきい値を変えるときは `tooling/quality-gates/src/index.ts` と対応する設定ファイルの
両方を直す（片方だけだとテストが落ちる）。
