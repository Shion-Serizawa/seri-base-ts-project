# 0002. 適応度関数（グッドハート対策）

- 日付: 2026-08-23
- 状態: 採用

## 背景

AI Coding では指標が「達成すべき目標」として直接最適化される。単一指標を置くと、
コードの質ではなく**指標の数値だけ**が最適化される（グッドハートの法則）。

代表的なハック:

- カバレッジ 80% → アサーションのないテストを大量に書く
- test ratio 下限 → テストをコピペで膨らませる
- 循環的複雑度の上限 → 意味のない小関数に分割して薄く散らす
- 複雑度・カバレッジの達成 → 巨大なライブラリを持ち込んで自前ロジックを消す

## 決定

**単独でハックすると別の指標が悪化する**組み合わせを適応度関数として設定する。
しきい値は `tooling/quality-gates/src/index.ts` に集約し、外部ツールの設定ファイル
（`.oxlintrc.json` / `stryker.config.json` / `.jscpd.json`）の数値と一致していることを
`tooling/quality-gates` のテストが検証する。**設定ファイル側だけを緩める**という
最も安易な抜け道を塞ぐのが目的。

### 牽制の構造

```
① カバレッジ 80%
   └ ハック: アサーションなしテスト
       ├ ④ ミューテーションスコア 60%（アサーションがないとミュータントが生き残る）
       └ vitest/expect-expect（そもそも lint で落ちる）

② test ratio 0.50〜2.50（下限と上限の両方）
   └ ハック: テストのコピペ膨張
       ├ ② の上限そのもの
       └ ③ 重複率 3%（jscpd はテストコードも対象にしている）

③ 重複率 3%
   └ ハック: 過度な共通化・抽象化
       └ ⑤ 複雑度（共通化した関数が太る）

⑤ 循環的複雑度 10 / ネスト 3 / 関数 50 行 / 引数 4 / 文 20
   └ ハック: 無意味な関数分割で薄く散らす
       ├ ⑥ knip（使われない export が出れば落ちる）
       └ ③ 重複率（分割した断片が似通れば落ちる）

⑧ バンドルサイズ予算（gzip）
   └ ①⑤ を「依存を足して楽をする」方向で満たそうとすると落ちる
```

### 強制する場所

「速いものは pre-commit、型情報が必要なものは pre-push、重いものは CI」で分けている。

| 指標                                     | 場所                                 | 理由                           |
| ---------------------------------------- | ------------------------------------ | ------------------------------ |
| 複雑度・`any` 禁止・層の境界             | pre-commit（差分）/ pre-push（全体） | oxlint は差分なら 1 秒未満     |
| カバレッジ                               | pre-push / CI                        | テスト実行が必要               |
| test ratio・重複率・デッドコード・サイズ | pre-push / CI（`bun run fitness`）   | 数秒                           |
| ミューテーションスコア                   | CI（PR、変更ファイルのみ）           | 全体実行では時間がかかりすぎる |

### `any` は割合ではなく error で禁止する

type-coverage による「型カバレッジ 99%」のような割合指標は、
残り 1% をどこに使うかの判断が属人化し、AI にとっては「1% までは `any` を書いてよい」
という指示になってしまう。次のルールで **error** として禁じる。

- `typescript/no-explicit-any`
- `typescript/no-unsafe-assignment` / `-argument` / `-call` / `-member-access` / `-return`
- `typescript/no-unsafe-type-assertion`（`as` による不正な絞り込みも禁止）
- `typescript/ban-ts-comment`（`@ts-expect-error` は 10 文字以上の理由必須、`@ts-ignore` は禁止）

## 却下した案

- **カバレッジ 100%**: 到達コストが指数的に上がり、意味のないテストを誘発する。80% + ミューテーションスコアの方が実質的
- **warn から始めて段階的に error へ**: AI は warn を無視して進むため牽制力が落ちる。空のリポジトリなので最初から error にしても既存コードの負債はゼロ
- **差分のみに閾値を適用（diff coverage 方式）**: 設定が複雑になる。レガシーを抱えた時点で再検討する
- **認知的複雑度（SonarJS）の別途導入**: oxlint の `complexity` + `max-depth` + `max-lines-per-function` + `max-params` の組み合わせでほぼ代替でき、ESLint 併用の保守コストを払う価値がない

## 運用

`bun run fitness` が 8 件をまとめて計測し、表で結果を出す。
しきい値を変えるときは `tooling/quality-gates/src/index.ts` と対応する設定ファイルの
両方を直す（片方だけだとテストが落ちる）。
