# 0002. 適応度関数（グッドハート対策）

- 日付: 2026-08-23
- 状態: 採用

## 背景

AI Coding では指標が「達成すべき目標」として直接最適化される。単一指標を置くと、
コードの質ではなく**指標の数値だけ**が最適化される（グッドハートの法則）。

代表的なハック:

- カバレッジ 80% → アサーションのないテストを大量に書く
- test ratio 下限 → テストをコピペで膨らませる
- 循環的複雑度の上限 → 意味のない小関数に分割して薄く散らす
- 複雑度・カバレッジの達成 → 巨大なライブラリを持ち込んで自前ロジックを消す

## 決定

**単独でハックすると別の指標が悪化する**組み合わせを適応度関数として設定する。
しきい値は `tooling/quality-gates/src/index.ts` に集約し、外部ツールの設定ファイル
（`.oxlintrc.json` / `stryker.config.json` / `.jscpd.json`）の数値と一致していることを
`tooling/quality-gates` のテストが検証する。**設定ファイル側だけを緩める**という
最も安易な抜け道を塞ぐのが目的。

### 牽制の構造

```
① カバレッジ 80%（ファイル単位）
   └ ハック: アサーションなしテスト
       ├ ④ ミューテーションスコア 60%（アサーションがないとミュータントが生き残る）
       └ vitest/expect-expect（そもそも lint で落ちる）

② test ratio 上限 2.50（下限は置かない。理由は後述）
   └ ハック: テストのコピペ膨張
       ├ ② の上限そのもの
       └ ③ 重複率 3%（jscpd はテストコードも対象にしている）

③ 重複率 3%
   └ ハック: 過度な共通化・抽象化
       └ ⑤ 複雑度（共通化した関数が太る）

⑤ 循環的複雑度 10 / ネスト 3 / 関数 50 行 / 引数 4 / 文 20
   └ ハック: 無意味な関数分割で薄く散らす
       ├ ⑥ knip（使われない export が出れば落ちる）
       └ ③ 重複率（分割した断片が似通れば落ちる）

⑧ バンドルサイズ予算（gzip）
   └ ①⑤ を「依存を足して楽をする」方向で満たそうとすると落ちる

⑨ シークレットの混入（gitleaks / 作業ツリー + git 履歴）
⑩ スキーマとマイグレーションの乖離（drizzle-kit）
   └ ⑨⑩ は牽制関係ではなく、型でもテストでも守れない性質のものを直接見ている
```

### 強制する場所

「速いものは pre-commit、型情報が必要なものは pre-push、重いものは CI」で分けている。

| 指標                                     | 場所                                 | 理由                           |
| ---------------------------------------- | ------------------------------------ | ------------------------------ |
| 複雑度・`any` 禁止・層の境界             | pre-commit（差分）/ pre-push（全体） | oxlint は差分なら 1 秒未満     |
| カバレッジ                               | pre-push / CI                        | テスト実行が必要               |
| test ratio・重複率・デッドコード・サイズ | pre-push / CI（`bun run fitness`）   | 数秒                           |
| ミューテーションスコア                   | CI（PR、変更ファイルのみ）           | 全体実行では時間がかかりすぎる |

### `any` は割合ではなく error で禁止する

type-coverage による「型カバレッジ 99%」のような割合指標は、
残り 1% をどこに使うかの判断が属人化し、AI にとっては「1% までは `any` を書いてよい」
という指示になってしまう。次のルールで **error** として禁じる。

- `typescript/no-explicit-any`
- `typescript/no-unsafe-assignment` / `-argument` / `-call` / `-member-access` / `-return`
- `typescript/no-unsafe-type-assertion`（`as` による不正な絞り込みも禁止）
- `typescript/ban-ts-comment`（`@ts-expect-error` は 10 文字以上の理由必須、`@ts-ignore` は禁止）

## 却下した案

- **カバレッジ 100%**: 到達コストが指数的に上がり、意味のないテストを誘発する。80% + ミューテーションスコアの方が実質的
- **test ratio の下限**: 当初 0.50 を下限として設定したが撤去した。理由は下記
- **warn から始めて段階的に error へ**: AI は warn を無視して進むため牽制力が落ちる。空のリポジトリなので最初から error にしても既存コードの負債はゼロ
- **差分のみに閾値を適用（diff coverage 方式）**: 設定が複雑になる。レガシーを抱えた時点で再検討する
- **認知的複雑度（SonarJS）の別途導入**: oxlint の `complexity` + `max-depth` + `max-lines-per-function` + `max-params` の組み合わせでほぼ代替でき、ESLint 併用の保守コストを払う価値がない

## test ratio の下限を撤去した理由（2026-08-24）

当初は「テストが薄すぎる状態」を検出するために下限 0.50 を置いていたが、次の理由で撤去した。

1. **良い書き方を罰する。** `it.each` によるテーブル駆動化は、テスト行数を減らしながら
   カバレッジとミューテーションスコアを上げる。下限があるとこれが減点になる
2. **量を足す方向の圧力になる。** 実際にこのリポジトリで、実装が増えてテストを整理した結果
   0.4986 になり、下限を満たすためにテストを追加した。今回は本当に抜けていた箇所
   （状態遷移の通し確認）だったので結果的に良かったが、判断が別方向に転べば水増しだった
3. **代替がある。** 「テストが足りない」の検出は、カバレッジを**ファイル単位**
   （`coverage.thresholds.perFile`）にする方が正確。集計だと、十分テストされた他のコードに
   紛れて「テストが 1 件も無いファイル」が隠れる

実際、perFile を有効にした直後に 2 件の実質的な穴が出た。片方は
`createQueryClient` のテストを消してしまった回帰、もう片方は
`api-client.ts` がテストで常にモックされていて一度も実行されていなかったこと
（`credentials: 'include'` を付ける fetch ラッパが未検証だった）。
LOC 比では検出できなかった種類の穴である。

**上限は残した。** 20 行の実装に 500 行のテストを書く方向（特に AI に「テストを増やせ」と
指示したとき）は、他のどの指標も測っていない。

## 型そのものの検査（2026-08-24 追加）

このリポジトリでは型が主要な成果物（branded type、oRPC の契約）なので、
`vitest --typecheck` による型テスト（`*.test-d.ts`）を `packages/contract` に置いている。
「型が緩くなる」方向の退化は実行時テストでは検出できない。

この型テストは導入直後に設計上の誤解を検出した。zod の `.brand()` が型を付けるのは
**出力側だけ**で、入力（`z.input`）は生の string のままである。つまり API 呼び出しの引数には
string を渡せる。branded type が守っているのは「受け取った id を他の string と混同すること」
であって、呼び出し時の入力ではない。この非対称性は型テストに固定してある。

## レビューで判明した穴と対応（2026-08-25）

第三者によるレビューで、実際に設定を改ざんして検証した結果いくつかの穴が判明した。

### 1. 「設定だけ緩める抜け道を塞ぐ」が複雑度の 7 つの数値にしか効いていなかった

最も強く主張していた防御が、実際には `complexity` / `max-depth` / `max-params` /
`max-statements` / `max-nested-callbacks` / `max-lines-per-function` / `max-lines` の
**数値 7 つしか見ていなかった**。以下の改ざんはテストを 1 つも落とさなかった。

```
"correctness": "error"       → "off"   （バグ検出カテゴリ丸ごと）
"typescript/no-explicit-any" → "off"
"vitest/expect-expect"       → "off"   （カバレッジ水増しの唯一の門番）
```

ゲートに詰まったときの最短の修復手段がそのまま通る状態だった。

対応: `tooling/quality-gates/src/lint-policy.ts` に Lint 設定のポリシーを宣言し、
`lint-policy.test.ts` が `.oxlintrc.json` との一致を検証する。

- `categories` は完全一致
- `error` にしているルールの集合が完全一致（消しても off にしても落ちる）
- `off` にしているルールの集合が完全一致（新しい off を勝手に増やせない）
- `warn` の使用を禁止（AI は warn を無視して進むため）
- `overrides` で off にできるルールを allowlist で制限（`typescript/no-unsafe-*` を
  ディレクトリ単位で黙らせる抜け道を塞ぐ）

上の 3 つの改ざんを再現し、3 件のテストが落ちることを確認した。

### 2. 層の境界がサブパス import で素通りしていた

`no-restricted-imports` を `paths`（完全一致）で書いていたため、`@seri/db` は止まっても
`@seri/db/schema` は通っていた（`@seri/db` は実際に `./schema` を exports している）。
また `apps/web` の制限リストには `@seri/api` しかなく、web → db は無防備だった。

対応: `patterns`（glob + `!` による許可）に変更し、各層を
「許可する依存先の allowlist」として書き直した。`@seri/db/schema` と
web からの `@seri/db` の両方がブロックされることを確認した。

### 3. デッドコード指標がテスト 1 本で無力化できた

`knip.json` の `entry` にテストファイルを入れていたため、テストから参照された export は
「使用中」扱いになっていた。**⑥ を無力化する行為が同時に ① カバレッジと
② test ratio を改善する**という、牽制構造が逆向きに働く唯一の箇所だった。

対応: 本番の入口を `!` サフィックスで明示し、`knip --production` を別ゲートとして追加した。
導入直後に「テストからしか使われていない export」を 5 件検出した
（`apps/api/src/index.ts` 全体、`RPC_PREFIX`、`apiOrigin`、`authClient`、
`todoContract`、`TODO_TITLE_MAX_LENGTH`）。いずれも削除または非公開にした。

### 4. バンドルサイズが未ビルドだと緑になっていた（false green）

`dist` が無いとき `ok: true` を返していた。pre-push は build を回さないため、
クローン直後や dist 削除後は常に PASS 表示だった。「計測できなかった」が緑で出るのは
最も危険な表示なので、**計測不能を失敗として扱う**ようにし、
pre-push に build を追加した（turbo のキャッシュが効くので差分が無ければ数百ミリ秒）。

### 5. test ratio が全体の 1 つの数値だった

どこが厚い／薄いのかが分からず、AI にフィードバックできなかった。
ワークスペース単位で算出・表示し、判定も各ワークスペースに対して行うようにした。

### 6. ミューテーションが PR のみだった

`if: github.event_name == 'pull_request'` だったため、main への直 push では ④ が走らず
① の牽制が外れていた。push でも走るようにし、差分の基準を
PR ならベースブランチ、push なら `HEAD~1` に切り替えるようにした。

### 対応しなかったもの

- **`apps/web/src/routes/**` が無防備**（テスト無し・カバレッジ除外・E2E 無し）。
  E2E を入れる段階でまとめて対応する

## 適応度関数そのものをテストした（2026-09-05）

上記 4 と 5 の不具合はどちらも未テストのスクリプトコードのバグだった。
「ゲートを実装したコードにバグがあると、ゲートが黙って緑になる」という壊れ方は
型検査でも他のテストでも捕まらないので、`scripts/` を計測とテストの対象に入れた。

### 何を変えたか

検査が `process.cwd()` と実際のプロセス起動に直接依存していたため、
そのままではテストできなかった。`FitnessContext`（`root` / `run` / `ci`）を
引数として渡す形に変え、テストは一時ディレクトリに作った擬似リポジトリと
差し替えた `run` に対して検査を走らせる。knip も gitleaks も起動せずに、
**終了コードの解釈・出力の整形・PASS/FAIL の判定**を検証できる。

`process.exit` を呼ぶだけの実行入口（`run.ts` 等）は判定ロジックを持たない数行に切り詰め、
カバレッジ計測から外している。判定は全て別モジュールにある。

ルートワークスペースのタスクは turbo の `//#` 記法で回す
（`turbo run test:coverage '//#test:scripts:coverage'`）。

### ⑥′ が設計を直した

内部ヘルパを「テストから呼ぶため」に export したところ、
`knip --production` が 13 件の未使用 export として検出した。
これは ⑥′ が想定どおりに働いた例で、**テストのためだけの export** を許すと
「テストを 1 本足して使用中にする」抜け道と同じことになる。
export を戻し、テストは公開している検査関数（`checkSizeBudget` など）を通す形に直した。

その過程で、予算超過の挙動を現実的な大きさのフィクスチャで検証できるよう
`checkSizeBudget(context, budget)` の第 2 引数を足している
（既定値は `QUALITY_GATES` のままなので単一情報源は変わらない）。

`packages/contract` から `docs/openapi.json` を生成し、コミット済みの内容と一致することを
検証する。⑩ スキーマとマイグレーションと同じ「型検査もテストも通るのに

## ⑬ Context の陳腐化（2026-09-05 追加）

`CLAUDE.md` と `.claude/skills/**/SKILL.md` が参照しているファイルパスと `bun run` の
スクリプトが実在することを検証する。文書が古くなる壊れ方は誰にも見えない。AI は
存在しないパスを黙って諦め、存在しないコマンドを打って別の理由で失敗するので、
原因が文書の陳腐化だと気づけない。lint も型検査もテストも markdown を見ない。

**牽制関係**: ⑬ を通す一番安易な方法は「文書を消す」なので、文書が 1 つも無い場合を
FAIL にしている（⑧ の未ビルドと同じ扱い）。逆に文書を厚くしすぎると参照が増えて
⑬ が壊れやすくなるので、`CLAUDE.md` を索引に徹させる圧力にもなっている。

バッククォートで囲まれたパスを拾う対象は、先頭がワークスペースのディレクトリ名
（`.claude` / `apps` / `packages` / `tooling` / `scripts` / `docs`）のものと、
ルート直下の既知の設定ファイル名（`.oxlintrc.json` / `stryker.config.json` など）に限っている。
`/api/rpc` のような URL や `<resource>.ts` のようなプレースホルダを誤検出しないため。

README.md 自身は対象に含めていない。`CLAUDE.md` からリンクされているので**存在**は
検査されるが、README が持つリンクの参照切れは見ていない。⑬ の目的は「AI に読ませる文書」の
陳腐化であって、人間向けの README まで広げると対象が際限なく増える。意図的な線引き。

導入の経緯と、Graph やエージェント基盤を入れなかった理由は
[0007-ai-coding-context.md](0007-ai-coding-context.md)。

### ⑬ が実装中に自分自身のバグを 2 件見つけた

- 内部ヘルパ `listContextDocuments` を不要に export していた（⑥ knip が検出）。
  ⑥′ が設計を直した件と同じパターン
- ワークスペースの scripts を `package.json` の**文字列一致**で探していたため、
  `@seri/db` に依存しているだけの `apps/api` を先に拾い、
  `bun run --filter @seri/db db:generate` を「存在しない」と誤答していた。
  `name` と厳密に突き合わせる形に直し、この誤認のテストを足した

2 件目は「FAIL するはずのないものを FAIL にする」側の誤りで、false green とは逆向きだが、
放置すれば「うるさいから」とゲートごと外される。実リポジトリに対して一度走らせるまで
気づかなかったので、新しい検査は擬似リポジトリのテストに加えて `bun run fitness` を
必ず通すこと。

### レビューで見つかった穴（2026-09-05）

別コンテキストのコードレビューで、⑬ に誤検出 1 件・検出漏れ 4 件・クラッシュ経路 1 件が
見つかった。実リポジトリでは PASS していたため、`bun run fitness` を通すだけでは
気づけなかったものばかりである。

| 種類       | 内容                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------- |
| 誤検出     | `bun run scripts/fitness/run.ts` の先頭セグメントを script 名として切り出し、「`scripts` が存在しない」と誤 FAIL していた |
| 検出漏れ   | タイトル付きリンク `[a](path "title")` が正規表現にマッチせず、参照切れを見逃していた                                     |
| 検出漏れ   | `--filter` のワークスペース名が `[a-z-]+` 限定で、数字を含む名前だと**その行ごと**検査対象から外れていた                  |
| 検出漏れ   | `.claude/` とルート直下の設定ファイルが対象外で、`CLAUDE.md` が名指しするファイルを検査していなかった                     |
| 検出漏れ   | スキルを 1 階層しか走査しておらず、階層化した瞬間に対象 0 件になった（⑬ 自身の false green）                              |
| クラッシュ | `JSON.parse` と `statSync` が裸で、壊れた `package.json` 1 つで `bun run fitness` 全体が他 12 件ごと死んだ                |

誤検出 1 件目は、`package.json` 自身が `"fitness": "bun run scripts/fitness/run.ts"` と
書いているのと同じ形式で、**リポジトリの実際の慣習を FAIL にする**ものだった。
現在の文書に該当記述が無かったため潜在的に留まっていた。上記の「うるさいから外される」の
再発である。

**教訓**: 適応度関数の正規表現は、リポジトリで実際に使われている書き方をテストケースに
入れる。実リポジトリで PASS することは「誤検出が無い」証明にはならない（まだその書き方を
していないだけ）。

## 「計測不能を PASS にしない」の取りこぼし（2026-09-05）

同じレビューで、この原則から外れている箇所が 6 件見つかった。いずれも
「ツールや環境が壊れた瞬間にゲートが黙って緑になる」形で、ADR 0002 が繰り返し
記録してきた事故と同型である。すべて FAIL 側に倒した。

| 箇所                       | 壊れ方                                                                       |
| -------------------------- | ---------------------------------------------------------------------------- |
| ⑩ schema drift             | `git status` の終了コードを見ず、失敗時の空出力を「変更なし」と読んでいた    |
| ⑧ size budget              | `dist` はあるが JS が 0 本のとき、合計 0 バイトを「予算内」と数えていた      |
| ⑨ actions pinning          | `.github/workflows` が無ければ PASS。消すかリネームすれば緑になった          |
| ② test ratio               | ソースが 1 本も無いとき比率 0.00 で PASS。ルート指定を誤ると黙って緑になった |
| `printReport([])`          | 検査 0 件で「すべて満たしています (0 件)」の終了コード 0                     |
| Stop hook `require-commit` | `git status` の終了コードを見ず、git が壊れると未コミット検出が無言で消えた  |

最後の 1 件は、同じコミット範囲で追加した `add-fitness-check` スキルが
「外部コマンドの `status === null` は FAIL」と規範を書いている、その隣の hook が
規範を破っていたもの。**スキルに書いた作法は、スキルの対象外のコードにも適用する。**

`isTestFile` が `path.split(sep)` で正規化していた件も同時に直した。`sep` は実行中の OS の
区切り文字なので、POSIX では Windows 区切りのパスが一切変換されない。テストが
「Windows でも同じ判定になる」ことを要求していたため、**CI（ubuntu-latest）では必ず落ちる**
状態だった。作者の Windows 環境でしか緑にならないテストは、ゲートとして意味を持たない。

## ⑭〜⑱ ISO/IEC 25010 の棚卸しで見つかった空白を埋めた（2026-09-06）

ISO/IEC 25010:2023 の 9 特性で現状を棚卸ししたところ、空白は 3 つだった
（信頼性・安全性・互換性の「破壊的かどうか」の判定）。9 特性を等しく扱うのではなく、
**空白を見つける分類として使い、証拠が今すぐ取れるものだけをゲートにした**。
検討の全体像と、入れなかったものは [0009](0009-iso25010-review-layer.md)。

### ⑭ 認可スコープをテーブル境界に閉じ込める

[0005](0005-authorization-and-cors.md) は「リポジトリ層のクエリはセッションのユーザーで
スコープする」を規約として書いていたが、**規約であって強制ではなかった**。
`where` 句にスコープを付け忘れたクエリを書く経路が残っていた。

`apps/api/src/repositories/todo-table.ts` を「生の `todos` テーブルに触る唯一の場所」にし、
公開するのは `userId` を閉じ込め済みの操作だけにした。ハンドラ側に `userId` が現れないので、
絞り込みを忘れたクエリが書けない。`.oxlintrc.json` の override で `@seri/db` を import
できるのを `apps/api/src/repositories/*-table.ts` と `apps/api/src/lib/auth.ts` に限定している。

**牽制**: allowlist をこっそり広げる抜け道は ⑪ が塞ぐ
（`tooling/quality-gates/src/lint-policy.ts` の `LAYER_IMPORT_POLICY`）。
**既存の ⑪ はこの穴を見ていなかった**ので、⑪ の管轄をここで広げている。

**残る穴**: `todo-table.ts` に「`userId` で絞らない操作」を足す経路は機械的に落ちない。
守っているのは公開する操作の型だけである。⑦ の依存方向と同じで、境界の内側の設計そのものは
人（とレビュー層）が見る領域として残る。

### ⑮ 契約が宣言したエラーの未実装

⑫ は「契約とドキュメント」の乖離を見るが、**契約と実装**の乖離は見ていなかった。
契約が `NOT_FOUND` を宣言していても、実装がそれを一度も送出しなければ、
型検査もテストも通り、生成される OpenAPI にも載る。クライアントは存在しないエラーに
対応するコードを書くことになる。⑫ と対で、宣言と実装の両側を見る。

逆向き（宣言していないエラーの送出）は oRPC の型が落とすので見ていない。

**限界**: 契約側と実装側をそれぞれ連結して**エラー名の集合**として突き合わせるので、
手続き A に宣言したエラーを手続き B が送出している場合は見抜けない。手続き単位の対応は
型と `apps/api/src/rpc/router.test.ts` の統合テストが担保する。

### ⑯ 公開 API の破壊的変更

⑫ は乖離しか見ない。**契約と一緒にドキュメントを再生成すれば、フィールドを消しても
必須項目を増やしても ⑫ は緑のまま通る。** README が「破壊的変更かどうかはレビューで
差分として見る」と書いていた部分を、決定論に置き換えた。

判定は「クライアントが依存できる公開面」の集合差分で行う。経路・操作・応答・フィールド・
列挙値が**消える**のは常に破壊的。**増える**うち破壊的なのはリクエストの必須項目の追加だけ
（応答側の必須追加や新しいフィールドの追加はクライアントを壊さない）。
集合で比較するので、整形の違いやキーの並び順では差が出ない。

**牽制**: 通す唯一の手段が Conventional Commits の `!` / `BREAKING CHANGE:` なので、
ゲートを回避しても履歴に必ず痕跡が残る。commit-msg フックが形式を検査しているのが前提になる。

### ⑰ 破壊的マイグレーション

⑩ も乖離しか見ない。列を消すマイグレーションを正しく生成すれば ⑩ は緑で通る。
D1 に巻き戻しは無く、失ったデータは戻らない。「型でもテストでも守れない性質のもの」
（⑨ シークレット・⑩ 乖離と同じ枠）として直接見る。

検出するのは `DROP TABLE` / `DROP COLUMN` / `DROP INDEX` / 既存列への `NOT NULL` 追加 /
`WHERE` 無しの `DELETE`・`UPDATE`。**「疑わしきは検出」ではなく「戻せないもの」に絞った。**
誤検出はゲートごと外される原因になるので、実リポジトリの drizzle の出力形式
（`ON UPDATE no action ON DELETE cascade` を含む `CREATE TABLE`）を誤検出しないことを
テストに固定してある。

**牽制**: 承認は SQL ファイル内の `-- destructive: <理由>`。コミットメッセージではなく
ファイル内に置くのは、承認がマイグレーションと同じ寿命を持つべきだからで、
後からファイルだけを見た人にも理由が残る。

### ⑱ 組み立てた DOM のアクセシビリティ

静的な JSX の不備は oxlint の `jsx-a11y` が見ているので、⑱ が見るのは
**組み立てた後の DOM の性質**だけ、という切り分けにした（Vitest 上で axe を実行する）。

**限界を明記しておく**: happy-dom にレイアウト計算が無いので `color-contrast` は無効、
best-practice タグ（`region` など）も対象外で WCAG タグのみに絞っている。
ヘルパを絞りすぎて常に空配列を返す false green は、名前の無いフォーム部品と
テキストの無いリンクを実際に検出させるテストで固定している。

### 実装中に既存ゲートが見つけたもの

- ⑥′ が `MAX_CONDITIONAL` を「テストのためだけの export」として検出した。
  ADR がこれまでに 2 回記録している同じパターンの 3 例目
- ⑤ の `import/max-dependencies`（上限 10）が `collect.ts` で落ちた。しきい値を上げるのではなく、
  検査を `groups/codebase.ts`（コードの形と供給網）と `groups/artifacts.ts`
  （生成物・契約・文書の乖離）の 2 群に分けた。数を通すためだけの分割ではなく、
  実際に性質の違う 2 群である
- 型検査が `secret-scan.test.ts` を止めた。`FitnessContext` の構造を書き下していたため、
  `baseRef` を足したときにそこだけ古いまま通る状態になっていた。型を書き下さず
  `FitnessContext` を使う形に直した

### ⑯ の基準リビジョンで false green を 2 回踏んだ

**1 回目**: 既定を `origin/main` にしていたが、このリポジトリにはリモートが無く常に FAIL した。
「うるさいから外される」側の誤りで、既定を `main` に変えた。

**2 回目**: `main` の上で作業していると基準と HEAD が同じコミットになり、差分が空になって
「破壊的変更なし」を返す。④ ミューテーションが PR のみで牽制が外れていたのと同じ形の穴である。
基準が HEAD と一致する場合だけ `HEAD~1` に落とし、**落としたことを結果に表示する**ようにした
（比較の幅が狭いこと自体が情報なので黙って落とさない）。

### `SAFE_REF` が `~` を許しておらず ④ が効いていなかった

⑯ を実リポジトリで走らせて見つかった。`scripts/mutation/changed.ts` の `SAFE_REF`
（シェルに埋めても解釈が変わらない ref 名の検査）が `~` を許していなかったため、
**CI が push 時に渡す `MUTATION_BASE_REF: HEAD~1` が弾かれ、④ の差分基準が黙って
作業ツリー差分にフォールバックしていた**。main への push で ④ の牽制が実質効いていない。
⑯ も同じ正規表現を写していたので、両方 `/^[\w./~-]+$/u` に直した。

`^` は許していない。`runCommand` は `shell: true` で走り、**Windows の cmd.exe では `^` が
エスケープ文字として食われる**ため、`HEAD^` は別の ref を指す。同じ理由で ⑯ の実装では
`git rev-parse --verify <ref>^{commit}` を使わず `git rev-list -n 1 <ref>` を使っている。
最初は前者で書いており、作者の環境でだけ「基準リビジョンを解決できない」と言い続けていた。

### 実リポジトリでの検証も一度失敗した

⑯ のユニットテストは 21 件すべて通り、`bun run fitness` も PASS していたが、
実リポジトリの `docs/openapi.json` からフィールドを 1 つ削って走らせると **PASS のままだった**。
原因は検査ではなく検証スクリプト側で、複数行の `node -e` が黙って実行されていなかった。
単一行に直したところ正しく FAIL した。

**「実リポジトリで走らせて確かめた」と書くときは、検証手段が本当に動いたかまで確かめる。**
ゲートが緑なのか、確かめ方が壊れているのかは、出力だけでは区別できない。

## ⑪ をテストから適応度関数に移した（2026-09-06 追記）

[0010](0010-base-repo-derivation-and-propagation.md) で A 層を派生リポジトリへ配ることに
したとき、⑪ の実装形態が問題になった。⑪ は `tooling/quality-gates` のテストとして
書かれていて、`../../../.oxlintrc.json` という**相対パスでリポジトリのルートを掘って**いた。
パッケージ化すると `node_modules` の中からルートを掘ることになり、そのままでは動かない。

`bun run fitness` の検査に移した。`context.root` を受け取る他の検査と同じ形になり、
派生リポジトリでも自分のルートに対して走る。テストのままにして派生側に薄いテストを
置かせる案も考えたが、**そのファイルを消すと ⑪ が黙って消える**。検査にしておけば、
差し込み漏れは `project checks`（件数の検査）が拾う。

移すにあたって 3 つに割れた。**割れたこと自体が層の境界を示している。**

| 検査              | 見るもの                                           | 層   |
| ----------------- | -------------------------------------------------- | ---- |
| `lint policy`     | カテゴリ・プラグイン・ルールの強度・適用範囲       | A 層 |
| `threshold drift` | `QUALITY_GATES` と oxlint / stryker / jscpd の一致 | A 層 |
| `layer boundary`  | 層の依存方向（⑦）と認可スコープ（⑭）の定義との一致 | C 層 |

`layer boundary` だけが C 層なのは、`@seri/contract` / `@seri/db` というこのテンプレート
固有のワークスペース名を持つから。ポリシーの宣言も
`scripts/fitness/project/layer-policy.ts` へ移した。

`tooling/quality-gates` 側には「宣言そのものが矛盾していないか」（重複、error と off の
排他、危険なルールの混入）を見るテストだけを残した。突き合わせる相手が壊れていると、
⑪ は緑のまま守れていない範囲ができる。

**牽制の相手は変わっていない。** ⑪ は全指標の前提であり続け、⑪′（`threshold drift`）が
「設定ファイル側だけを緩める」を、⑪″（`layer boundary`）が「allowlist に 1 行足す」を塞ぐ。
形と数値と境界の定義を別々の検査にしたので、片方が緑でももう片方が鳴る。

### 実装中に既存ゲートが 2 件検出した

- ⑥′（`knip --production`）が `checkProjectWiring` と `ProjectCheck` を
  「テストのためだけの export」として検出した。[0002](0002-fitness-functions.md) が
  記録している同じパターンの 4 例目
- `bun run lint` が `plugins` を計算して返し忘れていた実バグを
  `no-unused-vars` で捕まえた。extends 解決器の `plugins` が親のものをそのまま
  素通りしていて、和集合になっていなかった

## ⑲ テンプレート出自のドリフト（2026-09-06 追記）

[0010](0010-base-repo-derivation-and-propagation.md) でこのリポジトリを Template repository に
したとき、「この派生はどの世代の基盤から来たか」を知る手段が要った。基盤の改良を
どれに当てにいくかを決める起点になる値で、**これが無いと何を当てるべきかが決まらない**。

`.seri-base.json` の `ref` に自己申告させ、⑲ がその申告が壊れていないことを見る。

- ファイルが無い / 壊れている → FAIL。消した瞬間に常に緑になるのを避ける（⑬ と同じ扱い）
- `ref` が 40 桁の SHA でも `"template"`（テンプレート本体）でもない → FAIL
- `@seri/base-tooling` を引く全 manifest で SHA が一致していない → FAIL

3 つ目が実質的に一番効く。ワークスペースごとに違う SHA を引くと、同じリポジトリの中で
違う世代のゲートが混ざり、どのルールが効いているのか誰にも分からなくなる。

**`ref` が古いかどうかは見ない。** ネットワークに出ずに判定できないうえ、
[0010](0010-base-repo-derivation-and-propagation.md) の決定 7 で
「派生の事情を基盤が決めない」としている。古いこと自体は違反ではない。

牽制の相手は ⑬ と同じ形で、**自分の不在を自分で検出する**側にある。
