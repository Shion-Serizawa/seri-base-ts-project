# 0010. 派生リポジトリの作り方と、基盤改良の伝播

- 日付: 2026-09-06
- 状態: 採用

## 背景

このリポジトリは「個人開発用のベース」として作った。実際に使い始める前に、
運用上の疑問が 2 つ出た。どちらも**基盤と派生の関係**の問題である。

### 1. 新規プロジェクトを fork で作ると、コミットの独立性が失われる

fork の実害は履歴が全部入ることだけではない。GitHub 上で「forked from」の関係が残り、
Issue / PR / star が親に紐づき、派生から親へ誤って PR が飛び、ネットワークグラフも
親と同居する。派生は**別のプロダクト**であって、基盤の派生形ではない。

### 2. 基盤を改良しても、既に動き始めた派生には届かない

このリポジトリの価値は品質ゲートにある。ゲートは運用しながら育つ（実際 ADR 0002 /
0005 / 0009 はいずれも「動かしてみて穴が見つかった」記録である）。
**育った分が既存の派生に届かないなら、派生の数だけ品質が固定される。**

素朴な解は 2 つあり、どちらも採らなかった。

- **派生ごとに AI で強引に直す** — 派生が増えるほど線形にコストが増える。
  さらに「どの派生がどの世代の基盤か」を誰も知らないので、何を当てるべきかが決まらない
- **全部を 1 つの同期ツールで配る** — 設定ファイルには派生固有のカスタマイズが
  必ず入る（後述の `knip.json` が典型）。上書きすれば壊れ、3-way merge を組めば
  個人開発には重すぎる

## 決定

### 1. 基盤を 3 層に分け、層ごとに伝播の手段を変える

| 層    | 実体                                          | 伝播                                  |
| ----- | --------------------------------------------- | ------------------------------------- |
| **A** | ロジック（`tooling/*` のパッケージ）          | 依存を上げれば入る                    |
| **B** | 設定・作法。ルートに実体が要る                | A 層を `extends` する薄いラッパにする |
| **C** | サンプル実装、ADR、プロジェクト構造依存の設定 | 伝播しない                            |

**この分割自体が設計圧力になる**点が重要である。基盤を改良するときは
「A 層に置けるか」を先に問うことになり、置ければ伝播はタダ、置けなければ
派生ごとの手作業になる。この非対称性が、改良を正しい側へ寄せる。

### 2. 新規プロジェクトは fork ではなく Template repository から作る

GitHub の Template repository は fork ではない独立リポジトリを作り、
**初期コミット 1 個**から始まる。背景 1 の問題はこれで消える。

初期コミットに出自を刻むため、ルートに `.seri-base.json` を置く。

```jsonc
{ "template": "seri-base-ts-project", "ref": "<40 桁 SHA>", "syncedAt": "2026-09-06" }
```

**この値が無いと「どの派生がどの世代か」が分からず、背景 2 の判断ができない。**
A 層の依存も同じ SHA で固定するので、`ref` は基盤との接点を表す唯一の値になる。

### 3. A 層はレジストリに publish せず、git 依存 + コミット SHA 固定で配る

```json
"@seri/base-tooling": "github:Shion-Serizawa/<repo>#<40 桁 SHA>"
```

npm（公開・GitHub Packages とも）ではなく git 依存を選んだ理由は 4 つある。

- **publish 用の資格情報が存在しない。** レジストリ経由にすると
  「CI が汚染される → 自分の名前で汚染版が配られる → 全派生が踏む」経路ができる。
  防御を足すのではなく、攻撃面をそもそも作らないことで解く。
  [0003](0003-supply-chain.md) が Actions と mise に対して取ったのと同じ方針
- **コミット SHA で固定できる。** [0003](0003-supply-chain.md) の表は
  「npm パッケージはコミットハッシュ固定が不可」と記録している。git 依存はこの制約を
  回避し、`uses: owner/repo@<40 桁 SHA>` と同じ形になる
- **`minimumReleaseAge = 604800` を回避できる。** これが実務上いちばん効く。
  レジストリ経由だと**自分で直した基盤が派生に届くまで最短 7 日**かかる。
  基盤の改良は「自分が書いたコードを自分が引く」ので、公開遅延が守るものが何も無い
- private リポジトリのまま配れる。Template repository も private のまま使える

代償は、`bun install` が tarball を取る分わずかに遅いことと、Renovate 等の自動更新が
効きにくいこと。派生が数個の個人開発では問題にならない。

**公開 npm に出す理由は「他人に使ってほしい」以外に無い。** それが要るときに、
Trusted Publishing（OIDC）と Environment 承認を入れて改めて決める。

#### 実測で分かった制約: A 層は「1 リポジトリ = 1 パッケージ」でなければならない

Bun 1.4.0 で実測したところ、当初想定していた
「このリポジトリの `tooling/fitness` を git 依存で引く」は**成立しない**。

| 検証                                      | 結果                                                    |
| ----------------------------------------- | ------------------------------------------------------- |
| `github:owner/repo` の git 依存           | 動く。lockfile に SHA が記録される                      |
| `#<SHA>` でのコミット固定                 | 動く                                                    |
| サブディレクトリ指定（`#<SHA>&path:sub`） | **不可**。`&path:` が ref の一部として URL に埋まり 404 |

Bun は git clone ではなく codeload の tarball を取得して展開するため、
**リポジトリのルート `package.json` しか見えない。**

副次的な制約がもう 1 つある。依存としてインストールされたパッケージの `workspaces` は
展開されないため、A 層のパッケージ同士が `workspace:*` で参照し合っていると
（`fitness` → `@seri/quality-gates`）派生側で解決できない。

したがって **A 層は subpath exports を持つ単一パッケージに統合し、
専用リポジトリ `seri-base-tooling` のルートに置く**。

このリポジトリのルート `package.json` に兼務させる案も検討したが採らなかった。
派生の `node_modules` に `apps/` のサンプルまで丸ごと入るうえ、A 層内部の参照を
相対パスに落とす必要があって `tooling/*` の workspace 分割が形骸化する。
「1 リポジトリで済む」以外に利点が無く、その形骸化は時間とともに重くなる。

git submodule 案も採らなかった。SHA 固定と `workspaces` がそのまま効くのは魅力だが、
`clone --recursive` と CI の `submodules: true` を前提にする構成は AI に扱わせると
事故りやすく、[0007](0007-ai-coding-context.md) の「手順を増やさない」方針に反する。

**基盤リポジトリ自身もこのパッケージを引く。** ドッグフーディングされるので、
派生で壊れる前に自分が最初に気づく。

#### 実測で分かった制約: TypeScript のまま配ると Node からは読めない

`@seri/base-tooling` はビルドせず TypeScript のまま配っている。Bun はこれをそのまま
実行できるが、**Node は `node_modules` 配下の `.ts` を型除去しない**
（`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`）。どこが引っかかるかを切り分けた。

| 読み込む側                                    | 結果         | 理由                                      |
| --------------------------------------------- | ------------ | ----------------------------------------- |
| テストファイルからの `import`                 | 通る         | Vitest（Vite）が変換する                  |
| `bun run scripts/...`                         | 通る         | Bun のランタイム                          |
| `.oxlintrc.json` / `tsconfig.json` の extends | 通る         | JSON なので実行されない                   |
| **`vitest.config.ts`**                        | **通らない** | Vite の設定ローダーは Node が直接実行する |

境界は `vitest.config.ts` 1 か所だけだった。3 つの案を検討した。

1. **ビルド成果物を配る**（`dist` をコミットし、`src` との乖離をゲートで見る）— 最も
   一般的だが、ビルド手段（TypeScript 7 は emit が不透明）と乖離検査を新たに背負う
2. **`bunfig.toml` に `[run] bun = true`** を入れて Bun のランタイムを強制する — 1 行で
   済むが、**実際に試すと zod の解決が変わって `z.uuid is not a function` になった**。不採用
3. **しきい値だけ JSON でも配る** — `QUALITY_GATES` の数値を `quality-gates.json` として
   持ち、`vitest.config.ts` はそれだけを読む

**3 を採った。** 乖離させてはいけないのは「しきい値」であって、Vitest の設定を組み立てる
関数そのものではない。`createVitestConfig` は使う側にローカルで持たせる
（除外パスなどはどのみちプロジェクトごとに違う）。将来ビルド成果物を配るようになったら
共有に戻せる。

`lefthook.yml` と Claude Code のフックは `node` から `bun` に変えた。パッケージを
import するスクリプトは Bun でしか動かない。`bun` が PATH に無い環境では失敗するが、
失敗は push を止めるので黙って素通りはしない。

#### 実測で分かった制約: private リポジトリは git 依存で引けない

| 方式                           | 結果                                                            |
| ------------------------------ | --------------------------------------------------------------- |
| `github:owner/repo#SHA`        | 404。Bun は codeload の tarball を取り、`GITHUB_TOKEN` を見ない |
| `git+https://...`              | 同上（github.com は tarball API に正規化される）                |
| `git+ssh://git@github.com/...` | clone を試みる。SSH 鍵が GitHub に登録してあれば通る            |

`seri-base-tooling` は **public** にした。中身は汎用の品質ゲートだけで、シークレットも
ビジネスロジックも入っていない（`secret scan` が「混入なし」を返している）。
SSH 鍵を使う案は、CI で deploy key か PAT を Secrets に置くことになり、
**決定 3 で「資格情報という攻撃面を作らない」と決めた利点が一部失われる**ので採らなかった。

基盤リポジトリ（`seri-base-ts-project`）は private のままである。public なのは A 層だけ。

### 4. 適応度関数は「枠組み + 汎用検査」と「プロジェクトの形に依存する検査」に割る

A 層に移せるかは、検査がリポジトリの**形**を知っているかで決まる。実際に依存を見ると
きれいに割れた。

| 区分                       | 検査                                                                                      | 置き場所 |
| -------------------------- | ----------------------------------------------------------------------------------------- | -------- |
| 枠組み                     | `lib/`（context / exec / report / walk / bin）、`collect`、`groups`                       | A 層     |
| 形を知らない検査           | test ratio / duplication / dead code / secret scan / supply chain / context drift         | A 層     |
| しきい値で形を受け取る検査 | bundle size（対象ディレクトリを設定で受ける）                                             | A 層     |
| 形に依存する検査           | openapi drift / openapi breaking / schema drift / migration safety / contract error drift | **C 層** |

C 層の検査は oRPC の契約と Drizzle のマイグレーションという**このテンプレート固有の
構造**を直接読んでいる（`packages/contract/src`、`packages/db/migrations`、
`apps/api/src`）。派生がその構造を捨てれば意味を失うので、伝播させない。

代わりに A 層は**枠組みを export し、プロジェクト固有の検査を差し込ませる**。

```ts
// 派生リポジトリの scripts/fitness/run.ts
import { runFitness } from '@seri/base-tooling/fitness';
import { projectChecks } from './checks/index.ts';

process.exit((await runFitness({ extraChecks: projectChecks })) ? 0 : 1);
```

これは「共通ライブラリが枠を持ち、プロジェクトが中身を足す」形そのもので、
[0002](0002-fitness-functions.md) が `collect.ts` を 2 群に分けたときの延長にある。

**差し込みを任意にしない点が重要である。** 差し込みを忘れると C 層の検査が丸ごと
消えて「16 件すべて PASS」と表示される。⑬ が `CLAUDE.md` の不在を FAIL にし、
⑨ がワークフローの不在を FAIL にしているのと同じ理由で、
**想定より検査数が少ないこと自体を FAIL にする。**

### 5. B 層は「コピーするファイル」ではなく「extends する薄いラッパ」にする

これが背景 2 の後半（派生固有のカスタマイズとの同居）への答えである。
実ファイルを見ると、基盤由来の部分と派生固有の部分は同じファイルに同居している。
**同居したまま配ろうとするから難しくなる。** 中身を A 層に押し出せば、
ルートに残るのは派生固有の上書きだけになり、同期という問題自体が消える。

押し出せるかは機構の有無で決まるので、実際に確認した。

| ファイル                   | 機構                                                    | 結果                       |
| -------------------------- | ------------------------------------------------------- | -------------------------- |
| `.oxlintrc.json`           | `extends: string[]`（後勝ちマージ）                     | A 層へ                     |
| `lefthook.yml`             | `remotes:`（`git_url` / `ref` / `configs`）             | A 層へ。`ref` で固定できる |
| `stryker.config.json`      | extends 無し。`.mjs` 化して A 層の値を import           | A 層へ                     |
| `.github/workflows/ci.yml` | reusable workflow（`uses: owner/repo/...@<SHA>`）       | A 層へ。派生は caller だけ |
| `.claude/skills/`          | Claude Code plugin                                      | A 層へ                     |
| `knip.json`                | extends 無し。中身が `entry` / `project` = 構造そのもの | **C 層**（伝播しない）     |
| `CLAUDE.md`                | —                                                       | **C 層**（分割しない）     |

**押し出せないのは `knip.json` と `CLAUDE.md` の 2 つだけで、どちらも
「派生固有になるのが当然」のもの。** したがって 3-way merge が要るファイルは残らず、
同期ツールを作る必要も無くなった。

当初は `CLAUDE.md` の不変部分を `docs/base-rules.md` に切り出して参照させる案だったが、
実際に中身を数えると汎用なのは「Maker–Checker」と「ゲートを緩めるな」の 15 行ほどで、
残りは層の依存・oRPC・Workers という C 層だった。15 行のために ⑬ の参照面と
AI が読むファイル数を増やす価値は無い。**テンプレートには入るが、伝播はさせない。**

### 6. ⑪ は `extends` 解決後の設定を見る

5 の副作用として、**このリポジトリで最も重要な false green が 1 つ生まれる。**

⑪（lint 設定の改ざん検出）は `.oxlintrc.json` を直接読んでポリシーと突き合わせている。
`extends` 化した後もそのまま読むと、ルートのラッパには `categories` も `rules` も
書かれていないので、**ポリシーの大半が「検査対象に無い」状態になり、
`correctness: "off"` を足しても検出できなくなる。**

これは [0002](0002-fitness-functions.md) の「ゲートが 2 件黙って緑だった」、
[0005](0005-authorization-and-cors.md) の「8 つのゲートが全く鳴らなかった」と同型で、
しかも今回は**自分で作り込む**側にある。

したがって ⑪ は `extends` を再帰的に解決し、**マージ後の実効設定**に対して
ポリシーを検証する。こうすると、派生が `extends` を外しても、基盤のルールを
上書きで `off` にしても、どちらも同じアサーションで落ちる。

### 7. ドリフトは検出するが FAIL にしない

`.seri-base.json` の `ref` が古いこと自体は問題ではない。**派生の事情を基盤が決めない。**
適応度関数としては報告に留め、実際に取り込むかは派生側が判断する。

「今も保守しているものだけ直す」は、これで自然に実現する。A 層は依存更新のついでに
入るので、判断が要るのは C 層に落とした 2 ファイルだけになる。

## 入れなかったもの

| 見送ったもの                            | 理由                                                                         |
| --------------------------------------- | ---------------------------------------------------------------------------- |
| fork による派生                         | 背景 1。Issue / PR / star が親に紐づき、誤 PR が飛ぶ                         |
| 公開 npm / GitHub Packages への publish | 決定 3。publish 資格情報という攻撃面と、7 日の公開遅延が割に合わない         |
| B 層の 3-way merge 同期ツール           | 決定 5。extends で押し出せば不要。作れば「マージの正しさ」を誰も検証できない |
| `knip.json` の伝播                      | `entry` / `project` がプロジェクト構造そのもの。上書きすれば必ず壊れる       |
| ドリフトを FAIL にする                  | 決定 7。派生の事情を基盤が決めることになる                                   |
| 派生リポジトリの自動一括更新（bot）     | 派生ごとに文脈が違う。差分を当てる判断は AI + 人に残す                       |

## 残る穴

- **派生で基盤が改良されたとき、基盤へ戻す経路が無い。** 派生で見つかった穴を
  基盤に反映するのは手作業になる
- `.seri-base.json` の `ref` は自己申告である。実際に引いている A 層の SHA と
  ずれていても、ドリフト検知が両方を突き合わせるまでは分からない
- Template repository は「作った時点のコピー」なので、C 層（サンプル実装）は
  作成後に基盤側が直しても永久に届かない。これは意図した割り切りである
- lefthook の `remotes` は fetch を伴う。オフラインや初回 `bun install` 時の
  挙動は運用してみないと分からない
- `private: true` のリポジトリを git 依存で引けるかは未検証である。ローカルの
  `file://` git 依存は Windows の bun では解決できず、GitHub 上の実物でしか確かめられない
