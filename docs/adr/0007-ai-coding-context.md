# 0007. AI Coding 向けの Context 層を入れ、エージェント基盤は入れない

## 背景

このリポジトリは最初から「AI Coding 前提の品質ゲート」を中核に据えてきたが、
[README](../../README.md) の未着手節にある通り、AI 側に渡す Context（`CLAUDE.md`、
スキル）だけは手つかずだった。規約は README・ADR・`.oxlintrc.json`・
`tooling/quality-gates` に散っており、AI は毎回それを探し直していた。

判断の材料として、AI Engineer World's Fair 2026 の 5 トラック
（Forward Deployed Engineering / Context Engineering / Harness Engineering / Graphs /
Agentic Engineering）と、ループ・グラフエンジニアリングの統合を扱った資料を検討した。
どちらも **10〜30 名の組織・3〜5 リポジトリ・6〜9 か月で数千万円**という前提で書かれており、
そのままの規模では合わない。一方で、両者が「最優先」とする層
（決定論的な検証ゲート、ゲート自体の false green 対策、供給網の固定）は、
このリポジトリでは [0002](0002-fitness-functions.md) と [0003](0003-supply-chain.md) で
既に実装済みだった。

そこで「全部やる」のではなく、既に強い部分と実際に空いている穴を切り分けた。
穴は 2 つだった。

1. **Context 層が無い**
2. **Maker–Checker が分離していない** — 決定論的ゲートは強いのに、
   「仕様に合っているか」「ADR の判断に反していないか」は実装した本人の自己申告。
   [0005](0005-authorization-and-cors.md) の「8 つのゲートが全く鳴らなかった」と
   [0002](0002-fitness-functions.md) の「ゲートが 2 件黙って緑だった」は、
   まさにこの自己採点の失敗形として実際に起きている

## 決定

### 1. 知識の置き場所を、機械判定できるかどうかで分ける

「AI に伝えたいこと」を全部スキルに書かない。このリポジトリの流儀（規約は機械化する）に
合わせて、次のように振り分けた。

| 伝えたいこと                                             | 置き場所                                               |
| -------------------------------------------------------- | ------------------------------------------------------ |
| 依存の向き、`domain` の決定性、`any` 禁止、`os` ビルダー | `CLAUDE.md`（lint と型が落とすが、落ちる前に知る）     |
| しきい値変更で両方直す                                   | **既存ゲート済み**（`tooling/quality-gates` のテスト） |
| しきい値を変えたら README と ADR にも書く                | hook（機械判定できないが、編集は検知できる）           |
| 契約 / スキーマを変えたら再生成する                      | hook（⑫ ⑩ が落とすが、気づくのが早くなる）             |
| `collect.ts` の登録漏れ・テスト欠落                      | **既存ゲート済み**（⑥ knip と ① カバレッジ）           |
| API 手続きの追加手順、適応度関数の追加手順               | スキル（順番と参照先が多い）                           |

スキルを 2 件に絞ったのはこの振り分けの結果で、当初挙げていた「しきい値変更」は
既存ゲートと hook に降りた。

### 2. `CLAUDE.md` には詳細を再掲しない

索引と禁止事項に徹し、仕様と理由は README と ADR へのリンクにする。
再掲すると「README を直したのに `CLAUDE.md` が古い」という劣化が必ず起きる。
単一情報源の思想をそのまま適用した。

### 3. Context の陳腐化はゲートにする（⑬）

運用の約束ではなく `bun run fitness` で止める。詳細は
[0002](0002-fitness-functions.md) の ⑬ を参照。

### 4. Maker–Checker は「別コンテキストのレビュー」で足りるとみなす

参照した資料は独立 Verifier に別モデル・別プロセス・チェックポイント永続化を求めるが、
その大部分は「複数エージェントが並列に走る組織」の要請である。
開発者 1 名のこのリポジトリでは、**別コンテキストで走らせるレビューと、
既存の決定論的ゲート**でカバーできる。`CLAUDE.md` に規約として書いた。

## 入れなかったもの

後から「資料に書いてあったのに」と迷わないよう、理由とともに残す。

| 見送ったもの                                           | 理由                                                                                                                                                                                                                                                        |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Graph / Neo4j / オントロジー                           | 資料自身が示す導入判定 6 条件（100 サービス以上、lineage 横断、規制対応など）に**1 つも該当しない**。依存の向きは oxlint の `no-restricted-imports` が既に強制し、影響範囲は `tsc` が出す。資料側も Graphs トラックの多くがスポンサー枠だと自ら注記している |
| Forward Deployed Engineering                           | 顧客がいない。「本番の失敗を回帰テストに還元する」という核は既に普通の運用                                                                                                                                                                                  |
| LangGraph / Temporal / マルチエージェント基盤          | エージェント実行基盤の自作。ハーネスは Claude Code そのものなので二重実装になる                                                                                                                                                                             |
| 状態 DB / チェックポイント / OpenTelemetry span        | 監査の主体が 1 人。判断の記録は ADR が既に担っている                                                                                                                                                                                                        |
| OPA / サンドボックス / credential broker / kill switch | 個人の 1 台。`.claude/settings.json` の permissions と git で足りる                                                                                                                                                                                         |
| Cost per Accepted Change / chargeback / SLO            | 組織向けの会計                                                                                                                                                                                                                                              |
| 自動マージ・無人実行                                   | 資料も「ハーネスと評価が先」としており、順序として今ではない                                                                                                                                                                                                |
| MCP サーバの自作                                       | 今つなぐ先が無い。必要になってから                                                                                                                                                                                                                          |

## 結果

- `CLAUDE.md`、`.claude/settings.json`（permissions と PostToolUse hook）、
  スキル 2 件（`add-procedure` / `add-fitness-check`）を追加した
- 適応度関数が 12 件から 13 件になった
- ⑬ は実装中に自分自身のバグを 2 件検出した（不要な export と、
  ワークスペースの取り違え）。詳細は [0002](0002-fitness-functions.md) の ⑬

## 残る穴

- `apps/web/src/routes/**` が未検証（E2E 未着手）。Verifier の被覆としては
  これが最大の穴で、Context 層とは独立の既存課題
- hook が促すのは 3 パターンのみ。増やすと通知が騒がしくなるので、
  実際に忘れて落ちた事例が出てから足す
