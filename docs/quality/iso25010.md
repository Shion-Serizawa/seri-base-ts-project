# ISO/IEC 25010:2023 をレビュー観点として使う

このリポジトリは品質の大半を決定論的なゲート（適応度関数 ①〜⑰）で守っている。
**ここに書くのは、ゲートでは検出できない残りだけ**である。ゲートが見ているものを
レビューでも見ると、指摘がノイズで埋まってレビューごと回されなくなる。

観点の実体は [scripts/review/dimensions.ts](../../scripts/review/dimensions.ts) にある。
この文書はその読み物版で、**両者がずれていないことを
[scripts/review/route.test.ts](../../scripts/review/route.test.ts) が検証している**。
発火条件（どの変更でどの観点を起動するか）は
[scripts/review/route.ts](../../scripts/review/route.ts) が単一情報源で、
`bun run review:plan` が今回起動すべき観点を出力する。

## 使い方

```bash
bun run review:plan   # 変更内容から、起動すべき観点とその理由を出す
```

出力を `.claude/skills/quality-review/SKILL.md` の手順に従って観点ごとの
サブエージェントに渡す。**1 つのコンテキストで 9 特性を見ない。** 観点を混ぜると、
どれも浅くなる。

## 常に確認する 2 特性

| キー                     | 特性       | ゲートが見ていない部分                         |
| ------------------------ | ---------- | ---------------------------------------------- |
| `functional-suitability` | 機能適合性 | 依頼との一致、頼まれていない実装、境界値の抜け |
| `maintainability`        | 保守性     | 責務の置き場所、命名、意味上の重複、変更局所性 |

機能適合性は「① カバレッジ」「④ ミューテーションスコア」が**テストの厳しさ**を測るが、
**そのテストが正しい仕様を測っているか**は誰も見ていない。保守性は ③⑤⑥⑦⑪ が
形を測るが、**責務が正しい層にあるか**は測っていない。この 2 つが常設の理由。

この 2 軸は独立している。片方を通ってもう片方を落ちる変更がある。

- 規約どおりに書かれているが、作っているものが違う → 機能適合性が落ちる
- 依頼どおりのものだが、このリポジトリの流儀を壊している → 保守性が落ちる

**だから 2 つの報告を統合したり順位を付け直したりしない。** 片方がもう片方を隠す。

### 機能適合性は「照合先」を先に決める

この観点は照合先が無いと成立しない。次の順で探す。

1. 依頼された内容（Issue や会話）
2. ADR の判断
3. 契約（`packages/contract`）
4. 既存のテスト

**見つからなければ「仕様が無い」と報告する。** 照合先が無いことを「指摘なし」にすると、
何も見ていないのに通ったことになる。

### 保守性は名前の付いた症状で見る

「責務・命名・重複・変更局所性」という粗い切り口だけだと、レビューする側の語彙に依存して
見落ちる。Fowler『リファクタリング』第 3 章の症状を語彙として持たせている。
実体は [scripts/review/smells.ts](../../scripts/review/smells.ts) にあり、
この一覧との一致は [route.test.ts](../../scripts/review/route.test.ts) が検証する。

| 症状                   | どういう状態か                                           |
| ---------------------- | -------------------------------------------------------- |
| Mysterious Name        | 名前が、何をするか／何を持つかを表していない             |
| Duplicated Code        | 同じ形のロジックが複数箇所に現れている                   |
| Feature Envy           | 自分のデータより他のオブジェクトのデータを多く触っている |
| Data Clumps            | 同じ数個のフィールドや引数がいつも一緒に連れ立っている   |
| Primitive Obsession    | ドメインの概念を `string` や `number` のまま扱っている   |
| Repeated Switches      | 同じ型に対する分岐の連鎖が複数箇所に現れる               |
| Shotgun Surgery        | 1 つの仕様変更が散らばった修正を強いる                   |
| Divergent Change       | 1 つのファイルが無関係な複数の理由で編集されている       |
| Speculative Generality | 仕様が求めていない抽象・引数・拡張点がある               |
| Message Chains         | 呼び出し側が `a.b().c().d()` と内部構造を辿っている      |
| Middle Man             | ほとんど委譲しかしていないクラス・関数がある             |
| Refused Bequest        | 継承したもののほとんどを無視・上書きしている             |

**2 つの拘束がかかる。**

1. **リポジトリの規約が優先する。** README・ADR・lint 設定が是としている書き方は、
   症状に当てはまっても指摘しない。このリポジトリの規約は機械化してあるので規約側が正しい
2. **すべて判断であって違反ではない。** 言えるのは「Feature Envy の疑い」までである。
   確実に落とせるものは ③ 重複率・⑤ 複雑度・⑥ デッドコード・⑦ 層の境界が既に落としている

## 変更内容に応じて確認する 7 特性

| キー                     | 特性         | 主な発火条件                                                   | 既に落ちるゲート                           |
| ------------------------ | ------------ | -------------------------------------------------------------- | ------------------------------------------ |
| `security`               | セキュリティ | `apps/api/src/{repositories,rpc}/`、認証・CORS、契約、依存・CI | ⑨ シークレット、`os` の型強制、`bun audit` |
| `safety`                 | 安全性       | `packages/db/migrations/`                                      | ⑰ 破壊的マイグレーション                   |
| `compatibility`          | 互換性       | `packages/contract/src/`、`docs/openapi.json`、`packages/db/`  | ⑫ 乖離、⑯ 破壊的変更、⑩ スキーマ乖離       |
| `reliability`            | 信頼性       | `apps/api/src/`、`apps/web/src/lib/`                           | **なし**                                   |
| `performance-efficiency` | 性能効率性   | リポジトリ層、`packages/db/src/`                               | ⑧ バンドルサイズ予算                       |
| `interaction-capability` | 相互作用能力 | `apps/web/src/`                                                | ⑱ a11y（jsx-a11y と実行時 axe）            |
| `flexibility`            | 柔軟性       | `wrangler.jsonc`、ワークスペースの `package.json`、CI          | `process.env` 禁止                         |

**信頼性だけが「既に落ちるゲートなし」である。** タイムアウト・再試行・冪等性・
トランザクション境界は、このリポジトリで唯一まったく機械化されていない領域なので、
外部 I/O を触ったときは必ず見る。

同時に起動するのは常設 2 件 + 条件付き 3 件までにしている。個人開発で 9 本走らせると
重すぎて回さなくなる。上限で落ちた観点は捨てずに「今回は起動しない観点」として
出力に残る（黙って消すと、見ていないのに見たことになる）。

## 報告の形式: 主張ではなく証拠

「信頼性は大丈夫です」という報告は受け付けない。観点ごとに要求する証拠は
`dimensions.ts` の `evidence` にある。証拠を出せない指摘は「疑い」として
別に分けて出す。CLAUDE.md の「実際の終了コードと出力を見ずに『通った』と書かない」の
適用である。

## ゲート化していない理由（性能効率性・信頼性）

記事的な整理では、性能効率性は k6 や EXPLAIN 回帰、信頼性は Fault Injection で
証拠を取る。このリポジトリには**本番トラフィックも負荷も利用者もいない**ので、
その証拠は作れない。証拠を作れないものをゲートにすると「計測できなかった」が
緑で出る（[ADR 0002](../adr/0002-fitness-functions.md) が 6 箇所塞いだ壊れ方）ので、
レビュー観点に留めている。

QPS・SLO・データ量の常設コンテキストを置いていないのも同じ理由で、
**存在しない数字を書けば嘘になる**。

判断の経緯は [ADR 0009](../adr/0009-iso25010-review-layer.md)。
